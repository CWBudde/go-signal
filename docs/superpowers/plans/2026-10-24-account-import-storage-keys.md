# Storage-Key Lifecycle Implementation Plan

**Goal:** Complete Phase 16 Stage 2b so that every storage-key form signal-cli can hold (stored derived `storageKey`, `pinMasterKey`, `accountEntropyPool`) gives go-signal the same storage service key, and so that key sync updates keep the stored forms consistent.

**Architecture:** The mautrix-signal fork stores a derived storage service key next to `MasterKey` and the account entropy pool (schema v29, compatibility v29). One resolver, `DeviceData.ResolveStorageServiceKey`, turns the stored forms into a typed `store.StorageServiceKey`. Storage fetch, background sync, the connect-time key request and go-signal's facade all go through it. `ApplyStorageKeySync` decides how an authenticated `SyncMessage.Keys` replaces the forms.

**Spec:** `docs/superpowers/specs/2026-10-10-account-import-design.md`, "Storage keys and privacy reconciliation" (first paragraph) and the Stage 2b row; the source map is in `docs/account-import.md`, "Storage-key gap".

## Global Constraints

- Scope is Stage 2b only. Privacy guards, typed blocking, registry recovery, the converter and live acceptance stay open.
- `MasterKey` keeps its meaning. A derived key is never derived again and never turned into a master key. Invalid or disagreeing forms are refused, never guessed.
- Java vectors come from signal-cli's own key models (`com.github.turasa:models-jvm:2.15.3_unofficial_154`, the version v0.14.9 pins), pinned by checksum and generated by the existing harness. Go-side recomputation is no substitute.
- The fork release and the parent pin are immutable, with no committed `replace` or `go.work`. Commit to go-signal `main` and the fork's `purego` branch, then push.

## Decisions (approved 2026-10-24)

- **D1 Compatibility v29.** An older binary would ignore the derived key and could write a master key that disagrees with it, so older releases refuse upgraded databases, just as with v28.
- **D2 Legacy field without regenerating the schema.** Signal-Android reserves `SyncMessage.Keys.storageService` (field 1). The fork reads it from the message's unknown fields, so upstream's proto refreshes stay conflict-free.
- **D3 Superseding follows signal-cli.**
  - An entropy pool clears the older forms and is stored together with its master key (`setAccountEntropyPool`).
  - A legacy derived key replaces the derived form. It clears a master key or pool that no longer leads to it, because signal-cli would prefer the derived key from then on.
- **D4 Persistence before memory.** A keys update is written before the in-memory device changes. If the write fails, the handler fails and the message is redelivered. Invalid key material is logged and dropped.
- **D5 Reference checkout.** `reference/signal-cli` is pinned at v0.14.9-1 (`2a9a4b1`), the revision the Stage 1 corpus was generated from. Its storage and key handling are unchanged from the previous pin.

## Tasks

1. Harness: `StorageKeyVectors` plus `generate-account-import-fixtures.sh --storage-keys`. It adds models-jvm and kotlin-stdlib to the pom and checks their checksums. Output goes to `internal/signal/accountimport/testdata/java-storage-keys/`, which treefmt excludes.
2. Fork `store`:
   - `DerivedStorageKey`, `StorageServiceKey`, `DeriveStorageServiceKey`, `ResolveStorageServiceKey`, `ApplyStorageKeySync`.
   - Upgrade v29.
   - Pre-upgrade fixture rows use the old columns.
   - Tests: vectors, refusals, sync rules, persistence and reopening, and the v28 reader refusal.
3. Fork client:
   - `handleKeysSync`, the legacy unknown-field reader, `needsStorageKeys`/`HasStorageServiceKey`.
   - `FetchStorage(store.StorageServiceKey)`, `SyncStorage` and the connector go through the resolver.
   - Tests: Java manifest/legacy item keys, restart, superseding, refusals, persistence failure, connect decision.
   - Then release `v0.2609.0-purego.32`.
4. go-signal:
   - Pin bump.
   - `storedStorageKey` resolves through the fork. Invalid or disagreeing forms keep `account sync` asking for keys, and a blocked-list fetch reports them.
   - `just test-fork` runs the new tests.
   - Tests: the Java vectors file against the resolver, and the offline facade (master, derived only, conflict).
5. Docs: verification record, maintenance and dev notes, AGENTS.md, import map, spec status, PLAN.md.
